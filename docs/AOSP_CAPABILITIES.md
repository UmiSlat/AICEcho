# AOSP 设备能力检查与预置

## 当前实现

2026-10-09：应用新增“状态 → 设备能力检查”，配置页也有入口。无需选卡，无需开启高级模式。进入和刷新只读取能力，不导出、不恢复、不重载 NFC，也不更改默认钱包或系统备份设置。

后续源码已收敛为原 IDm 单一路线，能力比较和预置目标均直接使用当前卡片的原身份；生成/后缀兼容模式不再提供。缺少登记时的合法 `4000 + 02FE` 初始化仍是内部步骤，不是最终模拟身份。已构建 `3.0.0-original-idm-preview` / code 48，尚未安装；包信息见 [首版验收](3.0_ACCEPTANCE.md)。下方 code 47 的实机结果仍属于调整前的测试包。

| 检查项 | 含义与边界 |
| --- | --- |
| NFC / HCE-F | 系统特性声明及 NFC 开关；不代表射频已通过 |
| 当前卡片登记 | 只读公开 getter，与当前卡片路线比较；不显示原始卡号，不注册或启用服务 |
| Shizuku | API 13+，ADB shell UID 2000；当前仅主用户 user 0 |
| AOSP 服务 | `bu` 可执行，`bmgr --user 0 activated` 返回主用户服务已激活；未知结果不当作成功 |
| NFC 软件包 | `com.android.nfc` 存在、系统 UID、已启用且未停止、备份允许、代理及签名元数据可读 |
| 备份类型 | 有代理但未声明 `FLAG_FULL_BACKUP_ONLY` 时，提示标准路径通常仅支持键值备份 |
| 完整身份表 | 必须实际导出并解析 `f/dynamic_systemcode_nfcid2.xml`，旧本地快照不算本次 AOSP 验证 |
| 恢复 | 命令入口与实际读回分开；已有登记、退出码 0 或备份成功均不证明恢复成功 |

“验证完整备份”需要另外确认，可能触发 Android 备份确认并短暂影响 NFC。未返回归档、加密归档、缺少完整表、格式不兼容等有不同提示。用户取消或空输出不会当作成功，也不会自动重试或恢复。

## 标准路径

应用侧已经删除小米专用导出实现，不使用 `MiuiBackup`、厂商 `backupPackage`、ROM 版本白名单或固定小米签名。研究目录的旧工具与证据保留其历史用途，不是应用后备路径。

固定导出命令：

```text
/system/bin/bu backup -user 0 -noapk -noobb -noshared -nowidgets -nocompress -nokeyvalue com.android.nfc
```

`bu` 的 stdout 是二进制备份流，stderr 单独排空，不经过文本管道。当前支持标准 Android Backup v5，无密码，原始或 zlib 压缩 TAR；有总大小与解压大小限制。备份可包含常规完整备份数据域，应用只保留完整身份 XML，不把其他文件解包到磁盘。恢复归档只有 NFC manifest 和 CE 身份文件，manifest 使用当前设备的版本、SDK 和公开签名。

恢复仍使用标准 `bu restore -user 0`。文件路线保持“重新备份核对 → 系统确认恢复 → 重新备份读回”，所以一次写入可能出现三次系统确认。每次备份都不要设置备份密码。运行时重建路线见下文；两条读取路线都不可用时停止，不用单条登记拼出全局表，也不静默改走厂商接口。

键值代理仍允许主动验证标准导出。最新源码也允许“准备卡片”检查运行时基线，但这不等于已经允许写入；动态字段或范围不完整时明确停止。若标准导出已在当前服务会话返回完整身份表，文件后备可继续使用；声明完整备份的设备也仅能先尝试，实际取得基线才生成计划。

已保存的身份仍可通过“开始模拟”使用，只进行登记核对和前台启用，不要求重新导出。AOSP 导出失败不会删除已有卡片、登记或切换至模块路线。

- 旧版 2.2.23 的小米 ROM 写入与 HINATA 往返结果使用旧导出后端，不能视为本实现已通过。

## 候选路径：从运行时登记重建（2026-10-09）

标准导出失败，只否定当前完整文件读取方式，不证明必须使用厂商导出。用户提出从 `dumpsys nfc` 重建身份表，已完成源码和历史证据的离线核对。先接入只读检查和内存预览，随后接通下文的受限运行时预置；本节为离线研究记录，后续实机读取和准备结果见文末。

**支持证据：**同一轮历史设备快照中，dump 的两个 HCE-F 服务均能与完整 XML 按 component/UID 对应，System Code/NFCID2 一致。实际 ROM 的读取函数按 UID 分用户，接受可选的 `system-code` 和 `nfcid2` 属性。这说明当前设备的已观察身份可以成为重建候选，不必先拿到原始文件字节。

**不能直接照搬原提案的部分：**

- dump 使用 `getSystemCode()` / `getNfcid2()`，显示动态覆盖与静态声明合成后的值，而不是动态覆盖表本身。静态值与同值动态覆盖的 dump 相同，但应用更新静态声明后的行为不同；将所有生效值写成动态值是“当前值重建”，不能称为完整原表语义等价回滚。
- 动态 XML 可以只覆盖 System Code 或只覆盖 NFCID2。`NULL` 也是有意义的覆盖值，不能统一跳过；删掉它可能重新启用静态 System Code。遇到未解析或未分配的值，应报告不完整，不能静默丢失记录。
- 实际 ROM 的 dump 枚举当前用户及启用的关联资料，文件写入则遍历缓存中的多个用户。仅保留当前用户可能丢失其他用户动态记录；用户标题还是掩码名称，不能依名称推断用户 ID。应按 UID/用户清单核对范围，范围不足时不生成可写的完整表。
- 原文件 `NfcProvisionWorkflow` 在恢复后、重载前再次读取磁盘确认，然后才开放重载。dump 读取内存，恢复完成后可能仍显示旧值；不能直接替换 `snapshot()`。新运行时路线使用独立的“恢复已返回，待重载验证”状态，重载后再比对，不把退出码或进程变化当作生效证明。
- dump 的 T3tPmm 可比较服务配置是否变化，但不是射频实测 PMm，仍需外部读卡器核对。身份 XML 不包含 PMm。
- 只写自身的最小表会丢弃其他动态记录；生成过的随机 ID 也可能丢失，不能保证以后自动恢复原值。因此不把 `MINIMAL` 设为默认或自动兜底。
- 先通过公开 API 建立合法 `4000/02FE` 登记是本项目现有初始化流程，不是所有系统、所有已存在登记都必须执行的定律。已有目标登记不应被重复初始化覆盖；读取重建也不能保证其他 ROM 允许标准恢复。

后续实现采用“运行时来源与文件来源分开建模 + 按来源验证”，保留原始文件路径的字节级校验。运行时结果明确来源、用户范围、是否能区分动态属性及重载后验证层级，不能只添加枚举再把所有比较替换为 map 相等。它不要求为每个 ROM 实现专用导出，但仍有当前实现范围和系统恢复权限的限制。

仓库已有 `NfcIdentityAudit` 通过 shell 调用 `getNfcFServices(0)` 的成功证据。AOSP 的 `NfcFServiceInfo` Parcelable 含静态和动态字段，信息比普通 dump 更完整。已保存的本机 `framework-nfc.jar` 证实列表经 Parcelable 返回，但未包含 `NfcFServiceInfo` 类本体；此前探针只读 getter，没有证明该 ROM 可独立读取动态字段。已保存包信息还出现用户 999，dump 也有第二个用户标题，不能把当前设备当成已确认的单用户环境。

本地仅运行历史配对数据比较与三项合成 getter 模型检查；未编译 APK、连接手机、写入或重载。资料与结果在忽略的 `build/dumpsys-baseline-review-20261009`，不发布真实身份数据。

## 运行时检查入口

后续源码新增“设备能力检查 → 读取运行时登记”。只在点击后读取，不随页面进入、旋转、连接或普通刷新自动执行；无需选卡、完整备份或已激活的 BackupManager。此操作不备份、不恢复、不重载，不影响现有文件预置的判定，也不保存卡号或新建恢复计划。

- 优先通过 shell 的 `getNfcFServices(0)` 获取结构化对象，并尝试读取 `mDynamicSystemCode` / `mDynamicNfcid2`。区分属性缺省、显式 `NULL` 和字段访问失败；后者仍可显示“仅生效值”，不会伪装成原表。
- 结构化读取整体失败才尝试固定的 `dumpsys -t 4 nfc`。stdout/stderr 分离、有时间和 1 MiB 输出限制；严格解析完整 HCE-F 段，保留 NULL/RANDOM，拒绝截断、重复或未知格式。记录按 UID 推导用户，不依赖可重复或掩码化的用户名称。
- 结构化 Binder 调用在专用线程中执行，上层最多等待 2 秒；超时后走文本后备。由于 Binder 等待不保证响应线程中断，未返回的调用保留唯一占位，不以 `Future.cancel()` 假装结束，也不随重复点击累积线程或堵住共享 RPC 队列。该只读线程在实际结束或 UserService 退出时回收。
- 结构化主用户记录的动态字段全部可读时，在内存生成并校验 XML 预览。只写真正存在的动态属性，保留 NULL，不把静态值补成覆盖，不加入 PMm。空服务列表、其他用户或字段不可读不生成预览。结果页只显示来源、计数和预览结果，不展示原始身份。
- 预览仅对应已观察的用户 0 服务缓存，不是完整设备文件。其他用户、尚未初始化的缓存和未列出的登记仍不明；文本后备路径不生成可写 XML。只读 AIDL 为 14，最初接入时 UserService 版本为 7，后续运行时预置升至 8。
- 能力页检查仍然只读，不以其缓存摘要授权写入。准备卡片时另行采集完整范围并创建来源感知计划，详见下一节。

只读实现完成时尚未打包；随后 code 47 的安装和读取结果见下节。旧 `3.0.0-aosp-probe` / code 46 APK 不包含运行时检查入口。

只读阶段全量测试 511 项通过，无失败、错误或跳过；包含生产解析器对历史同轮私有 dump/XML 的配对核对、API 29/36 合成边界用例、动态字段不兼容降级、读取阻塞后走后备及后续刷新、界面和 RPC 限制。该阶段 Lint 0 错误、18 条提示，其中 14 条既有，新增 4 条是结构化读取使用隐藏 API 的兼容性提示；未屏蔽该限制。

## 运行时预置实现

- `NfcRuntimeBaseline` 使用 shell 的用户服务查询所有用户，只接受唯一、已解锁且当前为 user 0。首版不支持用户分身、工作资料或其他用户，不把未初始化或不可见缓存当成空表。历史设备记录出现用户 999；用户删除分身后，本机单用户基线检查已通过，尚不代表恢复写入已通过。
- 当前实现限 Android 14+；通过 shell 包管理 Binder 枚举 NFC-F 服务候选（包括禁用项），与两次结构化缓存读取按组件和 UID 对应。服务集、用户范围或动态字段变化时停止。所有动态字段必须可读；保留缺省、NULL 和单属性覆盖，纯静态项不冻结为动态值，未分配 RANDOM 不写入。
- `FILE` 计划保持逐字节比较；`RUNTIME` 计划按用户/规范组件/UID/属性比较，忽略 XML 排版、顺序及十六进制大小写，仍区分属性缺失和 NULL。XML 校验与记录键支持不同用户的同名组件，但这不等于开放多用户运行时重建。
- 准备优先尝试运行时来源。无法重建时，完整文件代理或本次服务会话已验证过完整导出的设备可以走标准文件后备；不会切回厂商导出，也没有 `MINIMAL` 后备。已有计划始终沿原来源检查，不在中途改变验证保真度。
- 运行时恢复正常返回后进入 `AWAITING_RELOAD`，不能再次写入、新建计划、回滚或启用模拟；只开放单独的重载步骤。重载后重新获取 Binder，等待服务缓存就绪，再采集并比较：候选一致才可模拟，原基线一致表示未改变，其余为冲突。恢复返回本身不证明写入，进程 PID 变化也不证明身份生效。
- 回滚基于最新观察合并本应用旧记录，保留其他应用的新登记；在调用恢复前，通过受限回调让应用原子保存实际 observation/replacement，保存失败不提交。重载后验证实际候选，而不是要求整个设备回到旧快照。回滚方向保留，不能误启用已被撤销的卡片。
- 计划存储升至 v2，保存来源、阶段、方向和回滚候选。写入/重载 IPC 前保存操作意图，收到稳定结果后先保存检查点、再清除未决日志。新会话先读取保存进度，未找回的待确认计划会阻止“准备新卡片”，等待重载计划不会因旧缓存仍存在而退回“准备完成”。
- 同次开机或 boot 不明时，丢失完成回执保持结果未知；服务独立读到新 boot 且与保存 boot 明确不同时，允许手动找回计划并按来源重新读取，不自动重放写入。v1 旧计划按文件来源兼容读取。
- 配置页面显示来源及等待重载结果；键值代理不再单独封死准备入口，而是在真实采集后报告具体范围或字段问题。只读诊断仍独立于备份能力。

最终本地验证：JDK 22 执行 `:app:testDebugUnitTest :app:lintDebug` 通过，620 项测试无失败、错误或跳过；Lint 0 错误、19 条提示（14 条既有提示及 5 条隐藏 API 兼容提示，未屏蔽）。覆盖来源比较、用户范围、取消/失败、先持久化再提交、待重载、重开门控、跨 boot 只读核验及回滚方向。两个子代理分别参与来源比较和采集实现，其中一个对整合后的检查点/状态机独立复审；发现的入口绕过、候选保存时序和跨 boot 找回问题已修复并补测试。`git diff --check` 通过。这些测试不证明真实设备允许读取隐藏字段或恢复身份文件。
